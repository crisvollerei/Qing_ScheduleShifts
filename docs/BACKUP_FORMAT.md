# 备份格式与兼容约定

文件备份和文本备份使用相同的数据结构与恢复流程。格式与校验位于 `assets/backup-format.js`，交互位于 `assets/data-tools.js`，排班由 `settings.restoreBackup`、标题由 `personalization.restoreTitle` 恢复。

## 数据版本：JSON v1

JSON v1 包含应用标识、数据版本、导出时间、当前排班、已保存方案和自定义标题：

```json
{
  "app": "qingzheng-schedule",
  "version": 1,
  "exportedAt": "2026-10-19T08:00:00.000Z",
  "config": {
    "version": 1,
    "anchor": "2026-10-19",
    "cycle": ["休息"],
    "shiftDefs": {
      "休息": {"emoji": "休", "cssClass": "rest", "isWork": false, "crossDay": false}
    }
  },
  "presets": [],
  "personalization": {"title": "清蒸排班"}
}
```

- `config` 保存当前排班；每个 `presets` 项保存同样的排班字段和一个非空、最多 40 个字符的 `name`。
- 工作班次另有合法的 `startTime`、`endTime`；所有周期名称必须有对应定义。日期、班次属性、类型、时间与周期使用同一套严格校验，不静默修复损坏的备份。
- `exportedAt` 为导出时的设备时间，仅作记录，不作为信任或覆盖本地数据的依据。
- 文件可能含本地方案的 `id`、`createdAt`；导入不采用外部标识，不以这些字段覆盖原有方案。
- `personalization.title` 是必需的单行标题，去除两端空白后长度 1–40 个 UTF-16 单位，不接受控制字符和行分隔符；与本地标题共用校验，并始终作为纯文本显示。缺少或无效时整份备份拒绝导入，不猜测默认值。
- v1 仅包含排班、方案和标题，不包含头像、主题、剪贴板或站点其他本地存储。导出只提取标题白名单字段；导入忽略额外头像字段，始终保留当前本地头像。
- 头像与标题共存在本地版本化记录 `qingzheng-personalization` 中，但该记录从不整体导出。若导入前排班的保护性保存失败，标题也只在当前会话应用，不覆盖原来的持久化外观记录；任何写入失败均明确提示备份另存。
- JSON 可有首部 UTF-8 BOM；可读文件采用缩进 JSON，文本载体采用紧凑 JSON。校验不要求属性顺序或特定缩进。

## 文本载体版本：QZB1

```text
QZB1.<payload>.<checksum>
```

1. `payload`：完整 JSON 的 UTF-8 字节，经 RFC 4648 Base64url 编码，使用 `-` 和 `_`，省略 `=` 填充。末尾填充位必须为零。输出为单行 ASCII，支持所有合法中文、表情和班次名称。
2. `checksum`：对编码前的完整 UTF-8 字节计算 CRC-32/ISO-HDLC，输出 8 位小写十六进制。参数为反射多项式 `0xEDB88320`，初值和最终异或均为 `0xFFFFFFFF`；标准 `123456789` 检查值为 `cbf43926`。接收端也接受大写校验值。
3. 接收端忽略文本载体中的 ECMAScript 空白（包含 CR/LF、空格和 BOM），因此复制自动换行不影响恢复。不自动提取聊天说明、Markdown 代码围栏、拼接的多份备份或零宽字符，避免误导入。
4. 先检查格式、版本、编码大小和校验值，再严格解码 UTF-8，最后走 JSON 数据校验。整个过程在应用数据前完成。
5. 文本输入也接受以 `{` 开头的当前格式原始 JSON 内容，由同一个 JSON 解析器处理。

CRC 用于发现复制缺失、意外修改，**不是签名、身份认证或加密**。拿到文本的人能还原其中的排班，也能生成新的校验值。不要公开分享；恢复来源仍应由使用者判断。

v1 不压缩，不依赖第三方库、网络、Web Crypto、安全上下文或可选压缩 API，以保持网站和单文件离线版的可读性。Base64url 会增加约三分之一长度；常规排班适合文本，方案非常多时文件备份仍更方便。

## 输入和资源限制

- 原始 JSON：最多 `2 * 1024 * 1024` 字节；同时限制字符串长度，并按 UTF-8 字节再次核对，避免多字节中文绕过限制。
- 粘贴文本：最多 `4 * 1024 * 1024` 个 UTF-16 代码单元，含换行与空白。界面 `maxlength` 与解析器限制一致。
- Base64url 在分配解码缓冲区之前检查解码长度，不得超过 JSON 字节限制；不支持无界解压或远程内容引用。
- 非支持版本、截断、无效 UTF-8、无效配置及超限数据均明确拒绝。错误不包含原始备份内容。

## 后续升级规则

两个版本号有不同职责，不能混用：

- **数据语义变化**：新增会影响恢复结果的字段、修改字段含义或结构时，提升 JSON `version`，在格式模块中新增版本读取与迁移分支，把历史版本转换为当前恢复模型。保留 v1 读取器；不可让旧应用把未知新字段静默丢弃后假装恢复完整。
- **载体变化**：更换编码、引入压缩或改变外层结构时，提升 `QZB` 版本，保留 QZB1 解码器。即使新载体携带的仍是 JSON v1，也不能挪用 QZB1 标识。压缩版本必须另加解压输出上限和对应安全测试。
- 只增加可忽略的展示元信息可保持数据版本；改变排班语义则不可。接收端对未知版本拒绝恢复、提示使用较新应用，不猜测兼容，不降级修复。
- 新导出可采用新版本，但迁移后的历史文件和文本必须继续使用相同的预览、确认、保留旧排班、重名处理和存储失败保护路径，不在界面层实现特例。
